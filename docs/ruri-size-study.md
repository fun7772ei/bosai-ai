# Ruri 30M・70M・130Mと検索改善の実比較

2026-10-14 UTC。今回の成果は**研究版の実装・実測・新規PRまで**。mainへのマージ・Pages更新は行わない。公開30Mベータを維持し、元bosai-appと原文88件は変更していない。自由生成LLMを戻していない。

結論はパターンC：**30Mを維持する**。今回のq8配布・CPU/WASM条件では70M/130Mの品質向上が一貫せず、負荷は増えた。意図・根拠ガードを実装したところ未収録/曖昧/冠水歩行の扱いは改善したが、否定を含む長文で誤棄却や別場面の選択が増えた。ガードの全面採用・公開既定変更も見送る。比較画面に旧条件/改善案を両方残し、次の開発は否定・場面関係と回答可能性の改善に絞る。310Mへ進む根拠は得られていない。

## ユーザーによるiPad結果

iPad第10世代/A14/RAM4GBのSafariで、ユーザーから30Mの読み込み成功、約25〜35ms、異なる3問成功、オフライン検索成功、目立つクラッシュなしとの報告を受けた。[報告記録](diagnostics/ipad-ruri-30m-user-report.json)。**短時間の基本動作は確認できた**が、開発側が実機を操作した結果ではない。

OS版/アプリ版/診断JSONは今回の報告では未取得。オフライン時の実行方式がRuriか軽量フォールバックか、実メモリ、長時間/大量検索、ホーム画面PWAとの同等性は未確認。70M/130Mは実機未確認。同じ3問を最初からやり直す必要はない。

## 固定したモデル・前処理

すべて実ONNXをTransformers.js4.3.1＋ONNX Runtime Web1.31.0-dev.20260914-8d85527a0で実行。ランタイムの依存更新は不要だった。CPU/WASM1スレッド、WebGPU無効、履歴なし、質問と文書に共通512トークン上限、超過時は切り捨てない。公式の上限8192より短いのはiPadの比較用資源制限。

|---|---|---|---:|---:|---:|
| 30M | onnx-community/ruri-v3-30m-ONNX | 1b41a27f31213fc55a9c4653c067770e39406408 | 256 | 37,048,575 | 43,778,410 |

形式はq8（dynamic int8の`model_quantized.onnx`）、Apache-2.0。Tokenizerは各公式`cl-nagoya/ruri-v3-*`の固定revision。全ファイルのURL・bytes・SHA256とTokenizer revisionは[models.json](../research/ruri/models.json)に固定し、実取得時に照合する。30Mは既存URL/revision/保存形式をそのまま使う。

70Mは公式ONNXではなく、onnx-community変換Spaceを使用したコミュニティ配布。q8 SHA `c0d9885f7cdd014518b25404b75b67b2072d93c49d0cc5509263b5e8a1994dfa`はmochiya98の配布にも一致した。配布の一致は独立した変換検証と同義ではない。[公式カード/グラフ調査](diagnostics/ruri-size-model-provenance.json)と[source](source/ruri-study/70m-README.md)を保持する。

全モデルに公式の`検索クエリ: ` / `検索文書: `を付与し、attention-mask mean pooling（prompt/特殊トークンを含む）→L2正規化→cosine。全88件の文書は同じtitle/summary/全steps/warning/keywordsでモデルごとに実計算した。ID順序・原文hash・モデルrevision/重みSHA・次元を検査し、異なるモデルや次元は拒否する。

70Mの出力名は`last_hidden_state`ではなく`token_embeddings`と`sentence_embedding`だった。初回は不一致で停止したが、グラフを調査しトークン出力へ対応。自前のmask meanとグラフのsentence embeddingがcosine≥0.99999で一致することも実推論で確認した。推論失敗の結果を成功として採点していない。

### 70Mの量子化診断

公式カードの5文のcosine行列との最大絶対差はq8で30M0.0168、70M0.0615、130M0.0205。70Mだけ同じ変換元のFP32 ONNXを**診断用に**追加実行すると差は0.000173、q8とFP32の文ベクトルcosineは約0.969〜0.980だった。[FP32対照](diagnostics/ruri-size-fp32-diagnostic.json)。少数例では量子化の寄与が示唆される。全重みの公式FP32との完全同一性を証明する試験ではない。

FP32は約280MBの重みを必要とし、モデル選択や今回の本比較には追加していない。この結果から「70Mというサイズ自体が劣る」と一般化しない。次に70Mを再検討するなら310Mへ拡大する前に、量子化/変換品質を調べる価値があるが、今回はq8の最終設定を変更しない。

## iPad向け判断と次のフェーズ

1. 最も現実的なのは**基本動作をユーザーが確認した30M**。70Mは約1.8倍の保存量/約1.7倍の温検索時間で、今回の正答/危険対応の優位が明確でない。130Mは約3.2倍の容量/約4.4倍の温検索時間で、さらに優位が弱い。70M/130Mを今すぐiPadに全取得させる理由はない。
2. 次の実装の中心は、条件/行動の構造化、否定された条件と質問の主題の区別、原文で回答できる範囲の判定。今回のガードを研究基盤として残すが、否定に弱いまま公開へ取り込まない。新しい開発問題とさらに別の独立評価を用意し、防災専門家のレビューも必要。
3. 30Mの既存3問は繰り返さず、次回は新しい入力10問程度の連続利用・解放/再読込1回・オフラインの診断JSONのactual方式確認を優先。公開版のJSONはrequested/actualがhybridまたはruriでfallbackなし、研究版はactualModel=30mを確認する。オフライン成功時にlightならEmbedding成功として扱わない。
4. Safariで通った結果とホーム画面PWAを区別し、PWA側の保存状態と再起動後1問を別記録する。アプリ/サイトデータを消さない。長時間/実メモリ/保存のOSによる管理は引き続き未確認。

研究版は今回Pagesへ出していないため、修正のiPad評価はレビュー後に同じbuildを実機で試せる場を用意してから行う。追加モデルが必要になった場合だけ70M一つを明示保存→非同時常駐の切替/10問/停止/解放/再初期化/オフラインactualModel確認、の最小手順にする。130M/310Mへの先行移行や自由生成LLMの復活は行わない。
