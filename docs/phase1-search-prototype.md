# Phase 1：88件の自然言語検索プロトタイプ

2026-10-14。今回のユーザー依頼により、Phase 1の比較実験として固定データの移植と検索画面を先行実装。正式なPhase 2統合・RAG・会話履歴には進めない。PR #7を継承し、マージ・Pages公開は行わない。iPad第10世代・iPadOS 26.5 Safariの今回の版は未確認。

## データと整合性

参照元は `fun7772ei/bosai-app` のcommit `e3aabdf0b85732b8d5de9b510fc2461acc59f8f4`、`data.js` のblob `881355b4a4b85a1da39515e8578aa5f74bb2644b`。ユーザーが明示した固定コピーの方針で移植し、元リポジトリは読み取りのみ。動的同期はない。

- 合計88件：津波17、避難所生活21、地震22、台風・大雨・停電28。
- [原ファイル](source/bosai-app-data.js) をバイト単位で保持し、[来歴](source/bosai-app-origin.json) にcommit/blob/SHA256を記録。[JSON](../src/bosai-data.json) のID・順序・カテゴリは元アプリに合わせた。
- タイトル・概要・準備品・全手順・注意事項・キーワード・優先度・出典のラベル/URLを保持。検索用正規化は索引にだけ適用し、表示原文を改変しない。
- `scripts/import-bosai-data.mjs --check` と、元アプリのパーサーを別に転記した `tests/bosai-data.test.js` で88件の全フィールドを照合。元ファイルのGit blob SHAも検証する。元データの防災内容が医学的・地域的に常に正しいことを証明するテストではない。
- JSONはViteでmain/CPU workerのJSに同梱し、既存の `shell.json` → Service Worker の保存対象となる。実行時にGitHub/Hugging Faceから辞書を取得しない。モデル重みは別途明示保存し、Git/Pages成果物には含めない。出典のラベル/URLはオフラインでも表示するが、リンク先の公的機関のページ自体はキャッシュしない。

## 実装した方式

1. **従来キーワード**：元アプリと同じ小文字化・空白区切りAND・部分文字列一致。対象はタイトル/概要/準備品/手順/キーワード、優先度順。空欄は何も推薦しない。
2. **軽量検索（既定）**：NFKC、かな表記の統一、`Intl.Segmenter` の語、文字bigram、一般的な言い換え語群を使用。タイトル/キーワードを重くし、概要/準備品/手順/注意も重み付きで参照。文書頻度によって一般的な語の重みを下げ、弱い一致は棄却し、上位3件を表示する。埋め込みモデル・外部APIは不要。
3. **軽量＋LFM350 / LFM700**：同じ軽量検索上位3件のタイトルと質問だけを渡し、最適な番号1～3、該当なし0を生成させる。1件だけでも棄却の余地を残すため選別を実行。候補が0件なら実行しない。文脈512・1スレッド・GPU層0・temperature0・履歴/プロンプトキャッシュなし。選別の出力上限は8 tokens、通常のPhase 1生成は従来の32/64のまま。

選別入力は120文字まで、軽量検索は200文字まで。LLMに88件全件や手順の全文を渡さない。今回の実測prompt token数は結果表に記載。長すぎる入力、エラー、不正な出力、停止・出力打ち切りは軽量検索へフォールバックする。LLMには単独の数字しか受理せず、生成した説明文・URL・防災助言は画面へ挿入しない。選んだ項目を先頭へ移動し、ほかの関連候補は残す。0が返った場合は該当なしとする。

生のモデル選別が軽量検索より良いとは仮定しない。モデル未準備の場合も検索は可能で、診断に `fallback-model-not-ready` を残す。既存のCPUセッションを再利用し、モデル/ネイティブWorkerを二重に読み込まない。処理中の停止・リセットと、その後の通常生成を維持する。アプリ更新によるモデル保存の削除は追加しない。

現在地の震度・今日の津波到達時刻・今開設中の避難所住所など、この静的データにないライブ情報の一部は検索前に棄却する。一般的なパターン検出であり、あらゆる未収録質問を検出するものではない。複数意図や曖昧な入力にも誤一致が残る。表示は参考の検索候補であり、確定した防災回答ではない。

## 評価方法

[40問](../scripts/search-cases.mjs)：通常10、直接キーワードの少ない言い換え8、曖昧3、複数情報4、該当なし5、危険な取り違え10。参照元の88件を読んで、人が正解候補と一部の危険な取り違えIDを付けた開発用セット。軽量検索の修正・しきい値確認にも使っており、独立した未見/専門家評価ではない。実災害の安全性や網羅性を示す数字ではない。

- 正解あり35問をTop-1/Top-3の分母とする。Top-3は「正解候補の少なくとも1件を含む」で、すべての関連項目が揃う率ではない。複数情報4問は関連項目の取得数も別集計する。
- 該当なし5問は棄却/誤提示を別集計。正解ありの空結果、誤Top-1、指定した危険な取り違えも区別する。期待した具体的な項目に一致しない候補の中には、同じ災害についての一般的な情報も含まれ、すべてを事実誤り・危険な助言と同一視しない。従来検索の空結果を正解としてTop精度に加えない。
- **同じ自然文**を全方式へ入力する。従来検索は全文一致に近くなり不利で、短いキーワードへ言い換えた検索能力を否定する比較ではない。例えば `トイレ 断水` なら元方式でも簡易トイレの項目が見つかる（回帰テストあり）。
- Linux Chromium、WebGPUを明示的に無効化、wllama/compat 3.8.1、CPU1スレッド。SHA256一致の固定GGUFをloopback fixtureからアプリの通常保存経路へ取得。モデルのID/revision/SHAは診断JSONに記録する。
- 本番previewで質問入力→方式選択→検索ボタン→結果カード/原文/出典表示をPlaywrightで全問検査。実際に非空のモデル出力とnative token数が取れた選別だけを「生成」に数える。候補0件・フォールバックは生成成功と数えない。
- 検索時間は同期検索。初回表示は候補DOM構築後のrAF＋次タスクまで（物理画面への描画完了を保証する値ではない）。LLM待ちの前に候補を表示する。完了はLLM選別と最終DOM構築まで。初回token/生成時間はnativeリクエストの実測。取得・モデル初期化・索引作成は別値。
- メモリは500ms間隔のLinux `/proc` PPid木のPSS合計とrenderer PSS。ブラウザ/保存/Blob/ランタイム等を含み、WASM heapやiPad使用量ではない。短いピークを見逃す。固定プロファイル・quota上書きなし。2モデルは並列推論せず順番に計測する。

## 結果

測定build **`0ab87a57417d`**。以下は最終版での同じ40問の結果（キーワード/軽量の時間は350M試験側）。モデルの取得時間・初期化は検索時間に含めない。

| 方式 | Top-1（35問） | Top-3（35問） | 誤Top-1 / 正解あり空結果 | 初回表示中央値 | 検索完了中央値 |
|---|---:|---:|---:|---:|---:|
| 従来AND（自然文をそのまま入力） | 0/35（0%） | 0/35（0%） | 0 / 35 | 13.7 ms | 13.8 ms |
| **軽量（採用・既定）** | **30/35（85.7%）** | **31/35（88.6%）** | **3 / 2** | **14.0 ms** | **14.2 ms** |
| 軽量＋LFM2.5-350M | 14/35（40.0%） | 31/35（88.6%） | 19 / 2 | 14.3 ms | 5.91秒 |
| 軽量＋LFM2-700M | 21/35（60.0%） | 31/35（88.6%） | 11 / 3 | 14.0 ms | 12.96秒 |

同期の検索処理だけなら従来0.1 ms、軽量0.6 ms。索引作成は初回約38 ms。LLM実行中も軽量候補は先に表示するので初回表示は速いが、確定する順位は数秒～十数秒後になる。全40問の完了中央値には、候補0件でLLMを実行しない7問を含む。**実際に生成した33件のLLM時間中央値は350Mで6.09秒、700Mで13.53秒**。初回token中央値は6.01秒/13.34秒で、出力が1桁でもprefill等の待ちが支配的だった。最大prompt token数は両方124で、文脈512を拡大していない。

| 方式 | モデル初期化 | 品質評価用実生成 | 検索段階のブラウザ全体PSSピーク / renderer | 危険質問10問のTop-1 |
|---|---:|---:|---:|---:|
| 軽量（モデル未読込） | 不要 | 0 | 257 / 126 MiB | 10/10 |
| ＋LFM350 | 2.22秒 | 33件 | 1,468 / 862 MiB | 2/10 |
| ＋LFM700 | 3.31秒 | 33件 | 2,048 / 1,135 MiB | 6/10 |

PSSはこのLinux Chromium全体の値でiPadの必要量ではない。軽量だけのもう一方の試行は261/129 MiB。メモリは取得/Blob読込/GCでも変わり、最終40問目は350Mで803/451 MiB、700Mで1,266/684 MiBだった。33件の順次選別・通常生成・停止・リセット・オフライン再読込でクラッシュ/生成エラーは両モデルとも0件だが、長時間・メモリ圧迫下の保証ではない。

該当なし5問は全方式5/5棄却・誤提示0。**LLM側の5問も軽量段階で候補0件となっており、LLMが未知質問を見抜いた結果ではない**。正解があるのに候補が出ない2問は赤白の旗と「水がない」。また候補に正解が入らなかった「座りっぱなし」について、700Mは0を返して誤提示を1件抑制したが、正解項目の検索には成功していない。

複数情報4問の関連8項目は軽量と両LLM方式で8/8保持。Top-3が両LLMで改善しないのは、基本的に同じ候補の順序だけを変える設計だからでもある。350Mは軽量に対してTop-1改善1問・悪化17問、700Mは改善1問・悪化10問。危険質問の期待項目不一致は350Mで8/10、700Mで4/10。事前指定した危険な取り違えペアでは両モデル1件（レベル5の質問でレベル3を選択）となった。この1件だけが危険だと断定する指標ではない。

### 採用判断

**今回はモデル不要の軽量検索を既定にする。LFM350の順位選別は実用採用しない。** 350Mは単一番号の形式には従えても、今回の日本語・タイトル3件という構成では意味に合った選別ができず、約6秒待って正しい順位を崩す。LFM700は350Mより正答が7問多く、誤った候補を1回棄却したが、軽量検索より9問少なく、約13.5秒・全体PSS約2GiBを要した。**iPadで700Mを新たに取得させるほどの利点は今回の結果にはない**。別プロンプト・要約付き候補等を網羅的に否定するものではないが、今回試した方式を自動採用する根拠は得られなかった。

検索プロトタイプの実装・開発側検証は完了したが、軽量検索にも誤一致・言い換え不足・曖昧さが残る。専門家の未見評価とiPad Safariの最小確認を経るまで、正式Phase 2統合・防災回答システムの完成とは扱わない。

## 回帰・失敗・未確認

最終版で **Node24の54テスト、本番ビルド、ダミー保存/更新互換、モデル不要の画面検証、40問×2方式の軽量再確認、2モデルの実GGUF検証が成功**。[検証一覧](diagnostics/search-validation.json)、[保存互換（ダミー）](diagnostics/search-storage-browser.json)、[画面検証](diagnostics/search-ui-check.json)、[390px画面](diagnostics/search-prototype-mobile.png)。WebGPU無効のCPU試験であり、Safari実機の代替証明ではない。

- 88件全フィールド一致、不正LLM出力・候補外番号・停止時のフォールバック、入力長、通常生成との設定分離を単体検査する。
- 元の保存transaction/中断/再読込/旧形式互換テストを維持。ダミー重みの保存・更新互換テストは実GGUFやiPadの証明と区別する。
- 実GGUF試験は40問の後の通常生成、選別の途中停止・リセット、Chromiumのオフライン再読込後の軽量検索とLLM選別まで行う。PWAをiPadでインストールした検証ではない。
- `npx playwright install --with-deps chromium` はroot切替の認証権限不足で失敗。既存環境のChromiumは起動でき、`npx playwright install chromium` は成功。最初の試行はpreview未起動で接続拒否、起動後に再実施した。
- 分かち書きの表記チャネル修正前の測定を最終結果へ混ぜない。カタカナをかな変換してからだけ分割すると歯ブラシ等の語境界を取りこぼすため、元表記の分割結果も併用した。比較途中の700Mブラウザは再測定のため意図的に終了し、モデル非互換とは扱わない。
- 長時間・OSメモリ圧迫・Safari/PWA再起動後の保持・iPadの発熱/消費電力・今回の版のSafariクラッシュ有無は未確認。


## 次のiPad確認（公開・実施は別途）

1. レビュー後の版で、Safari通常タブから軽量検索だけを先に試す。モデル取得・PWA削除は不要。寝ているときの地震、高台に間に合わない津波、断水トイレの3問で、原文の注意事項・出典まで開けるか確認。
2. 未収録の「今日の津波の到達時刻」と、曖昧な「水がない」の表示を確認。特定できないのに確定した答えとして受け取らせないかを観察。
3. LLMの比較を行うなら保存済みLFM350を再利用し、同じ3問だけで追加待ち時間・誤選別・停止/リセットを記録する。全モデル取得や40問の反復を要求しない。700Mは開発結果に利点があると判断した場合だけ別途検討。
4. 今回もiPadのPWA/オフライン確認は後回しという希望を維持。ブラウザのネットワーク遮断試験の成功を「完全オフライン完成」と言い換えない。
