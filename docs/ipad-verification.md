## 最新：CPU版で次に試す最小限の手順

対象は **iPad第10世代・iPadOS 26.5・Safari**。LFMのWebGPU版も入力を変えると3件目前後で落ちるとの追加報告がある。下記の古いWebGPU手順より、このCPU比較を優先する。クラッシュ原因は未確定で、CPUなら確実に動くという結果はまだない。

1. オンラインで公開ページを開く。旧Safariタブとホーム画面アプリを閉じて開き直し、「CPU/WASM比較」が選べることとアプリ版 `64ece2a7b9b6` を記録する。サイトデータ・既存モデルを削除しない。
2. 「LFM2.5-350M（CPU/WASM比較）」を選ぶ。Q4_K_Mを一度保存する（約229MB、ONNXとは別）。保存後にページを再読み込みし **1/1ファイル、55分割** が残ることを確認する。失敗したらJSONを保存し、推論へ進まない。
3. 読み込みを一度実行し、生成可能を確認。上限 **32トークン** で、①「日本語で1から5まで数えてください。」②「今日は晴れです。をそのまま書いてください。」③「集合は午前9時、図書館の入口です。この文を短くしてください。」を順に試す。入力を変えても完了するかと、内容が保持されるかを別々に記録する。3件目の前にもJSONを保存しておく。
4. 通ったら停止→別入力の生成→実行をリセット→再読み込みを一度確認する。落ちたら同じ試行を繰り返さず、再起動後の「前回は…」とJSONを保存する。
5. JSON保存後、機内モード＋Wi-FiオフでSafariを閉じて再起動。同じURLでCPU版・保存済みのみを選び、読み込みと短い生成を一度試す。
6. Safariで通った後、オンラインでホーム画面へ追加し、PWA側でも保存状態を確認する。共有されていなければPWA側で取得する。PWAを閉じ、機内モード＋Wi-Fiオフで再起動して読み込み・生成を確認する。Safariの成功をPWAの成功として記録しない。

最初はこの短い確認だけでよい。速度・品質・発熱・最後の段階・Safari終了/ページ再読込の種類を記録する。通ってから入力を変える10回と30分程度の試行へ進む。開発側のChromium実モデル検証とiPad実機結果は区別する。[CPU比較結果](phase1-cpu-results.md)。

## LFMの10回成功後に残る最小確認

ユーザー提供JSONでLFM / q4f16の初期化と短い生成10回の完了を確認した。Gemmaは連続生成中に落ちたとの報告があり、同じ試行を繰り返す必要はない。LFMを第一候補として、次を優先する。

1. 同じ形式・上限64トークンで「日本語で1から5まで数えてください。」と、与えた短い文章の要約を各一度試し、指示に従うかを見る。自己紹介の10回出力は同一で不自然だったため、生成成功と品質を分ける。
2. JSONを保存し、Safariの対象タブを閉じる。機内モード＋Wi-Fiオフで再び開き、LFM / q4f16・保存済みのみモードで初期化し、短い生成を一度試す。これが未確認の再起動後オフライン利用の確認になる。
3. 上記が通った後に停止・リセット・再初期化と長時間利用を確認する。初回の10回完了は約18秒の短い試行で、30分の安定性を意味しない。

結果の根拠と限界は [ユーザー実機結果](phase1-user-results.md)。新規利用の初期選択をLFMへ変更した版は `7ca23c3c9e36`。既存の選択がGemmaの場合は手動でLFMを選ぶ。保存削除は不要。

## 次に試す最小限の手順（Cloud修正の公開後）

1. オンラインで公開ページを一度開き、`bosai-ai`の旧Safariタブをすべて閉じてから開き直す。更新が旧タブの終了を待つため、画面に「アプリ版」が出ることを確認し、その値を記録する。サイトデータ・モデル保存は削除しない。ホーム画面アプリは後で別途検証する。
2. q4f16を選び「ダウンロードして保存」を**一度だけ**押す。エラーならそこで止めてJSONを保存する。「Worker起動完了」、エラーの `stage` / `name` / `message`、`appBuild` を共有する。Safariが終了した場合は再度開き、「前回は…」とJSONを記録する。
3. 保存完了なら再読み込みし、q4f16の5/5とIndexedDBの分割表示を確認。「モデルを読み込む」を一度だけ試す。落ちたら生成へ進まず、最後の段階を記録する。
4. 準備完了なら最大64トークンで「日本語で1から5まで数えてください。」を生成する。成功時にJSONを保存し、タブを閉じ、機内モード＋Wi-Fiオフで開き直して同じ形式を読み込み、同じ入力を生成する。

保存が成功しても推論の実機成立とは別。初期化で再度Safariが終了するなら同じ試行を繰り返さず、Qwen3必須の成立は保留として辞書中心の軽量方式を優先する判断材料にする。以下の長時間・停止・ホーム画面検証は、この短い確認が通ってから行う。

まず「ダウンロードして保存」だけを試し、完了したらページを再読み込みする。その段階で落ちた場合は推論を試さず、最後の表示を記録する。保存完了後に「モデルを読み込む」を試し、再度落ちた場合は次回起動時の「前回は…」表示を記録する。推論初期化で引き続き落ちる場合は、Qwen3のiPad対応は不成立として軽量検索を優先する。同じクラッシュを何度も繰り返す必要はない。

保存方式はIndexedDBの4MiB分割へ変更済み。再読み込み後に「選択中のq4f16: 5/5ファイル保存済み」「モデル本体: IndexedDB・…分割 / …MB」が残るか確認する。提供ログでは旧Cache APIでモデル本体の保存がInternal errorで失敗していたため、必要なのは新方式での保存成功の確認。5/5が揃うまで推論は試さない。

1. iPadOSのバージョン、iPad第10世代であること、空き容量、検証日時を記録。Safariの通常タブで公開HTTPS URLを開く。最初はオンライン。数百MBのモデルと実行ファイルを取得するため十分な空き容量を用意する。
2. 画面のWebGPUとshader-f16を確認。q4f16で「ダウンロードして保存」をタップ。保存完了後にページを再読み込みして「モデルを読み込む」。ファイル進捗、読み込み時間、最後の処理段階、エラー、ページの応答性を記録。読み込み停止・クラッシュ時は再起動し、その条件を記録する。shader-f16非対応時のみq4を比較する。q4はメモリ負荷を下げるための選択肢ではない。
3. 初期の自己紹介を生成し、日本語の出力、初回トークン秒数、tokens/sec、生成トークン数、所要時間を記録。続いて「日本語で1から5まで数えてください。」などの入力で再現性を確認。防災に関する入力も可能だが内容の正しさの検証は辞書統合後に行う。
4. 最大256トークンで生成し途中停止。再生成できるか確認。「実行をリセット」でWorkerを終了し、再読込できるか確認する。
5. 「10回連続テスト」を実行。複数回繰り返して30分程度の利用、画面回転、背景移動からの復帰を試す。発熱、速度低下、Safari再読み込み、クラッシュを記録する。停止ボタンで残りの連続生成も止められる。
6. 「保存状態を更新」をタップ。モデルファイル・重みの保存件数と使用量、永続保存リクエストの結果を記録。診断ログの「アプリ本体のオフライン保存完了」を確認。**件数だけでオフライン動作確認済みと判断しない。**
7. JSONを保存してからSafariタブを閉じる。機内モードをオンにしWi-Fiもオフにする。Safariを再起動して同じURLを開く。「保存済みモデルのみ使用」をチェックし、同じ形式で再読み込み、日本語生成を確認する。OSがSafariを終了しても再利用できるか試す。取得なしのエラー、再読み込み時間、速度を保存する。
8. オンラインに戻してホーム画面に追加。**Safariタブとホーム画面アプリでストレージが共有されるとは限らない。** ホーム画面側でも初回取得→終了→機内モード→再起動→生成を確認する。
9. オンラインで「実行をリセット」→「モデル保存を削除」。保存のみモードで読み込めず、通常モードで再取得できるか確認する。q4とq4f16は別ファイルで、形式変更時には追加ダウンロードが必要。
10. 正常・異常の両方で「検証結果をJSON保存」。JSONに端末型番、OS、Safari/ホーム画面、オンライン/機内モードを添えて結果を記録する。JSONには質問・出力を含むので個人情報を入力しないテストで共有する。
